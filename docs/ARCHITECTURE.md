# Архитектура

Редакция v1.0 · **Требования и техническая детализация.** Стек и детали — П-01/02/03/07; публикация — Р-20…Р-25. Код реализован; текущие проверки — IMPLEMENTATION.md.

## Минимальный подход

Предлагается клиентское статическое веб-приложение: TypeScript, Vite, семантический HTML и CSS. UI-фреймворк, роутер и глобальная библиотека состояния не требуются для нескольких экранов и одной игры. Это проектное решение под текущий объём, а не утверждение, что другие технологии непригодны.

Vite предлагает TypeScript-шаблон и статическую сборку. Версии Node.js и пакетов проверяются в момент T01 по официальным требованиям и фиксируются в package.json/lockfile. `vite preview` предназначен для локальной проверки, не для постоянного размещения. Источники: [Vite guide](https://vite.dev/guide/), [Static deploy](https://vite.dev/guide/static-deploy.html), проверены 21.11.2026.

## Компоненты и ответственность

| Модуль | Ответственность | Не должен делать |
|---|---|---|
| content | Локальная валидированная колода, справочники, deckVersion | Редактировать тексты или запрашивать сервер |
| domain | Доступные карточки, выбор, переходы, инварианты | Обращаться к DOM, IndexedDB, сети |
| application | Принять действие, построить кандидат, сохранить, принять переход, отобразить ошибку | Дублировать правила выбора в обработчиках кнопок |
| storage | Прочитать/проверить/записать/удалить снимок; конфликт вкладок | Сбрасывать данные молча |
| ui | Экраны, управление фокусом, рулетки, краткие правила | Считать показанной карточку независимо от контроллера |
| offline | Полный кеш выпуска, признак готовности, обслуживание закреплённого выпуска | Хранить ответы, управлять выбором вопросов |
| tests | Содержательные проверки контента, логики, сохранения и браузера | Выдавать эмуляцию за реальный телефон |

## Предлагаемая структура будущего проекта

Это логические ориентиры, а не уже существующие пути. Перед каждой задачей проверять репозиторий.

```text
src/
  content/       колода и справочники
  domain/        модели, переходы и случайный выбор
  application/   контроллер игры
  storage/       адаптер сохранения
  ui/            экраны и стили
  offline/       регистрация и статус готовности
tests/
  unit/          логика, контент, снимок
  e2e/           браузерные сценарии
scripts/         подготовка контента/списка ресурсов при необходимости
public/          только необходимые статические ресурсы
docs/            документация
sources/         исходники для сверки, не для публикации
```

Не помещать проектную документацию или исходные TXT/XLSX в public. Изображения и шрифты извне не обязательны; системный шрифт с кириллицей уменьшает размер и сетевые зависимости. Новую библиотеку добавлять только при установленной необходимости.

## Взаимодействие и интерфейсы

- Источник случайности: функция, возвращающая число в [0,1); тесты подставляют фиксированные значения и проверяют границы интервалов.
- Контент: получить колоду и найти вопрос по ID; не читать Excel в runtime.
- Логика: получить действие и снимок, вернуть кандидат нового снимка либо причину невозможности перехода. Алгоритм не выполняет запись.
- Хранилище: read → отсутствует / валиден / повреждён / несовместим / недоступен; save → успех / ошибка / устаревшая revision; clear → успех / ошибка. Не возвращать неоднозначное null при всех ошибках.
- Контроллер: сериализует действия и обеспечивает commit-before-render; повтор сохранения использует прежний кандидат.
- UI: рендер по состоянию, без отдельной независимой копии списка показанных. Временное состояние анимации и диалога отделено от снимка игры.
- Офлайн-слой: сообщает «подготовка / готово / ошибка / обновление доступно», не выводит непроверенное «готово» только по navigator.onLine.

## Навигация и браузерная кнопка «Назад» — П-04

Маршрутизация внутри одной страницы, без серверных API и URL для каждого вопроса. Назад из глубины ведёт к теме без выдачи карточки. На карточке системное «Назад» вызывает тот же безопасный путь смены выбора; повторное «Назад» на теме может покинуть страницу, снимок остаётся. Закрытие браузера не зависит от диалога beforeunload. Browser Forward не должен заново запускать случайную выдачу или возвращать старые снимки; UI восстанавливает текущее принятое состояние, а не историческую карточку.

## Хранение

Предлагается IndexedDB для одного снимка и служебной привязки к выпуску. Причина — не объём 60 ID, а транзакционная запись и возможность чтения активного выпуска из service worker, когда страницы ещё нет. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) описывает транзакции и доступ из worker. localStorage для этого не подходит: он недоступен в service worker. DATA_MODEL.md задаёт схему и ограничения. Библиотека-обёртка не обязательна.

Ресурсы приложения сохраняются service worker в Cache API. Для работы service worker нужен защищённый контекст: в семейном размещении HTTPS; localhost — исключение для разработки. HTTP-адрес компьютера в локальной сети не следует считать доказательством автономной работы на телефоне. Источник: [MDN Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API).

Браузер может удалять локальные данные и кеш: [MDN storage limits and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Приложение не хранит семейные истории и не обещает их резервирование.

## Автономность и обновления — П-07

1. Сборка формирует точный список ресурсов полного выпуска, включая колоду, CSS, JS, иконки и HTML. Не кешировать лишь уже посещённые темы.
2. Service worker сначала полностью готовит отдельный кеш buildId. При сбое не считать выпуск готовым, рабочий кеш не удалять.
3. Клиент подтверждает полноту кеша и возможность обслуживания текущего адреса; только затем показывает готовность офлайн. В первом визите учитывать установку/активацию/получение контроля страницы.
4. Для автономного холодного запуска навигация обслуживается HTML текущего согласованного выпуска, а его хешированные файлы — из того же кеша. Чужие origin не кешировать.
5. Новая версия устанавливается отдельно. Отсутствия skipWaiting недостаточно: браузер может активировать ожидающий worker после закрытия всех клиентов. Поэтому snapshot и стабильная служебная запись activeRelease с buildId сохраняются в IndexedDB одной транзакцией. Новый worker читает activeRelease до обслуживания навигации и при активной игре возвращает HTML и ресурсы закреплённого выпуска, даже если сам worker уже новый.
6. Формат activeRelease стабилен между выпусками; новый worker обязан читать его без изменения снимка игры. Не удалять базу или старые stores при обновлении worker. При неизвестном формате показать безопасную ошибку, а не новую игру. На активной странице не перезагружать UI автоматически.
7. После завершения игры (атомарного удаления snapshot и activeRelease) предложить применить готовый новый выпуск. Если пользователь выбирает новую игру при доступном обновлении, сначала предложить обновление, затем создать новую игру уже на выбранном выпуске. Отказ оставляет текущий выпуск.
8. Старый кеш очищается только если он не закреплён activeRelease и не обслуживает открытые клиенты. Все хешированные ресурсы принадлежат конкретному buildId. T08 проверяет два выпуска, автоматическую активацию после закрытия всех вкладок, холодный офлайн-возврат и потерю сети.

Автоматическая активация после закрытия старых клиентов описана в [MDN: замена service worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers#replacing_an_existing_service_worker). Закрепление полного выпуска через activeRelease — предлагаемое проектное решение, а не встроенная гарантия браузера; оно требует реализации и теста T-13.

PWA-манифест входит в MVP по последнему решению пользователя: start_url/scope/id соответствуют подпапке репозитория, display=standalone, локальные PNG-иконки 192 и 512 px, русское имя. Стандартная установка через Chrome возможна, но не обязательна для игры; собственного навязчивого приглашения установки нет. Push-уведомления не нужны. При смене origin сохранение и кеш не переносятся автоматически.

## GitHub Pages и область приложения

Разработка — в отдельном подключённом GitHub-репозитории, основная ветка main. Node.js LTS >=22 используется из существующей среды, совместимость Vite проверяется до установки. В Actions — та же согласованная ветка из .nvmrc. Workflow проверяет PR без публикации, а main после успешных проверок публикует только dist через Pages artifact. Постоянный URL имеет вид https://<owner>.github.io/<repository>/. Фактический адрес Pages — https://alyona-zvezden.github.io/nashi-istorii/.

Vite base задаётся как /<repository>/ из единого BASE_PATH при сборке. Все URL ресурсов, worker и manifest формируются из этого base. Регистрация worker — /<repository>/sw.js со scope /<repository>/; fetch/navigation fallback не перехватывает запросы вне этой области. Имя IndexedDB, кешей и канала сообщений включает идентификатор приложения/репозитория: разные project sites одного owner делят origin, поэтому одной URL-подпапки для изоляции хранения недостаточно. Подробнее — DEPLOYMENT.md.

## Сборка, окружение и тесты

Предлагаемые scripts описаны в README, фактические появятся в T01. Production build должен включать typecheck, подготовку/проверку контента и автономных ресурсов. Vitest используется для чистых правил и ошибок хранения; Playwright — для сборки в Chromium, mobile viewport, сети и service worker. Официальные источники: [Vitest](https://vitest.dev/guide/), [Playwright emulation](https://playwright.dev/docs/emulation), проверены 21.11.2026.

Секретов и .env для пользовательских API нет. Если будущий хостинг требует учётных данных, они не входят в клиентский пакет и документацию. В dev service worker должен быть выключен либо явно изолирован от production, чтобы не выдавать старые файлы при разработке. Полная проверка офлайна выполняется на production build.

## Android и будущее

Не добавлять серверные сущности архива и Android-обёртку заранее. Отделённая игровая логика и стабильный контент помогут следующему этапу. После пилота отдельно сравнить улучшенную веб-версию, оболочку и самостоятельное Android-приложение по требованиям, стоимости и способу распространения.
