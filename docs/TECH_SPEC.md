# Техническое задание

Редакция v1.0 · 21 ноября 2026 · **Согласованный MVP; среда и публикация уточнены пользователем.**

Согласованные продуктовые и инфраструктурные решения — Р-01…Р-26 в DECISIONS.md. Нормативные формулировки ниже описывают будущую реализацию; П-01…П-08 — авторская инженерная детализация, а не утверждение об отдельном выборе пользователем каждого параметра. Изменение согласованной механики требует решения пользователя; внутренние уточнения должны быть согласованы между документами.

## 1. Назначение продукта

«Наши истории» — семейная разговорная игра с цифровой колодой вопросов. Телефон помогает выбрать вопрос, затем уступает место разговору. Будущий архив не входит в текущую реализацию.

## 2. Цели и критерии успешности

Техническая цель — полностью работоспособная игра на одном Android-телефоне в Chrome, включая автономную работу и восстановление. Обязательны все Must Have и согласованные краткие правила. Приёмка — раздел 20 и TEST_PLAN.md. Продуктовая цель — проверить интерес к повторным семейным разговорам; предложенный пилот описан в PRD.md, его результаты не подменять успешной сборкой.

## 3. Границы текущей версии

Включены: колода, две рулетки, ручной выбор, мини-раунды, пропуск, смена выбора, исчерпание, завершение и новая игра, сохранение и восстановление одной активной игры, автономная работа, краткие правила. Исключены: аккаунты, персональные профили, редактор, дополнительные вопросы, ответы, микрофон, фото, сервер данных, синхронизация, статистика, книга, платежи, Android-пакет и публикация в магазинах.

## 4. Целевая аудитория

Первый тест — мама и дочка. Точный возраст неизвестен. Один общий телефон. Дальнейшая аудитория — разные поколения семьи; не добавлять возрастные ветки и фильтры без решения пользователя.

## 5. Пользовательские роли

Одна программная роль: участник с общим доступом к экрану. Понятие рассказчика или администратора отсутствует. Человек, держащий телефон, не получает дополнительных прав и не оценивает ответы.

## 6. Сценарии и User Stories

US-01…US-10 описаны в PRD.md. Экранные переходы — UX_FLOWS.md. Каждый критичный сценарий связан с FR и проверками T-01…T-21 в TEST_PLAN.md.

## 8. Экраны и навигация

UX_FLOWS.md задаёт: выбор темы, выбор глубины, карточка, исчерпание, восстановление, подтверждение сброса/завершения, нейтральное завершение и ошибки. Основной вход без снимка — сразу темы; отдельная рекламная или регистрационная заставка не нужна.

## 9. Игровая логика и алгоритмы

Множество доступных: `колода ∩ выбранная тема ∩ выбранная глубина − shownIds`. Для n>0 выбрать индекс равномерно из [0,n). Источник случайности передавать в игровую логику как зависимость для воспроизводимых тестов; не выбирать сортировкой со случайным компаратором. Криптографическая стойкость для этой игры не требуется.

Рулетки отдельно выбирают индекс из шести тем и трёх уровней; их выбор не зависит от количества карточек и shownIds. Визуальная остановка точно соответствует заранее выбранному результату. Нельзя сначала выбрать карточку из всей колоды, а затем объявить её тему: это изменит согласованные вероятности.

У мини-раунда нет счётчика обязательного прохождения. Новая игра — единственная операция сброса истории помимо завершения. Повторный вывод текущей карточки после восстановления не является новым выпадением.

## 10. Контент и нумерация — П-04

В Excel поля «Вопрос», «Тема», «Уровень глубины». Для первой импортированной редакции предлагаются ID q001…q060 в порядке строк 2…61 и displayNumber 1…60. ID после назначения не пересчитывать при перестановке. Уровни хранить числами 1/2/3, текст названий выводить из справочника. Исходный текст не нормализовать с заменой знаков и окончаний. Контроль совпадения — по всем 60 записям, не только по количеству.

## 11. Модель данных

DATA_MODEL.md: Deck, Question, SessionSnapshot, справочники темы/глубины. Никаких сущностей Member, Answer, Recording, Family или серверных таблиц в MVP. Отдельно version схемы снимка, deckVersion контента и buildId ресурсов.

## 12. Хранение и синхронизация — П-02/03

Один структурированный снимок и привязка к выпуску в IndexedDB; готовые ресурсы выпуска в Cache API. Нет синхронизации или архива игр. Чистый игровой модуль не обращается к браузерному хранилищу напрямую. В браузере данные могут быть удалены пользователем или механизмами очистки; не обещать бессрочную сохранность. Разные origin и профили Chrome имеют разные данные. В приватном режиме долговременное восстановление не гарантируется.

## 13. Архитектура — П-01

Небольшое клиентское приложение: UI → контроллер → чистая игровая логика, адаптер сохранения и локальная колода. Service worker отвечает только за автономный выпуск. Сервер пользовательских данных отсутствует. Полная структура и границы — ARCHITECTURE.md.

## 14. Стек — П-01

TypeScript, Vite, HTML/CSS без UI-фреймворка; Vitest для логики, Playwright для браузерных сценариев. Использовать существующую Node.js LTS >=22, проверить минимальную patch-версию и поддерживаемые ветки выбранного Vite. В T01 зафиксировать одну совместимую LTS-ветку для локальной среды и Actions, версии зависимостей и lockfile; не устанавливать latest при каждой задаче. Не выбирать библиотеку Android заранее.

## 15. Разрешения устройств

Не нужны микрофон, камера, местоположение, уведомления и контакты. Пользователь не обязан устанавливать приложение. Загрузка веб-ресурсов и обычное локальное хранение — техническая основа, без запроса доступа к личным файлам.

## 16. Конфиденциальность и безопасность

В игре нет записываемых ответов и персональных профилей. Показанные ID и текущее состояние остаются на устройстве. Не отправлять события игры наружу, не подключать аналитику, рекламу, API ИИ или удалённые шрифты. Тексты выводить как текст, не как исполняемый HTML. В браузерной сборке только ресурсы приложения и колода, без sources/, документов и локальных путей.

Сетевой хостинг выбран: GitHub Pages, нужен для начальной загрузки и обновлений. HTTPS обязателен. Обычная ссылка без пароля согласована; приложение доступно каждому, у кого есть адрес. Отдельно определить видимость исходного репозитория: обычная ссылка на игру не означает разрешение опубликовать личные контекстные заметки. Серверная БД и авторизация не используются. Политика технических логов определяется GitHub, не обещать полного отсутствия логов.

Аудио и несовершеннолетние: реализация записи исключена; юридические процедуры не придумывать. Если запись будет включена позднее, отдельно согласовать территорию использования, согласие, доступ, удаление, резервное копирование и передачу историй.

## 17. Ошибки и нестандартные ситуации

Обязательны: пустое сочетание; все карточки показаны; пропуск последней; двойной тап; перезагрузка во время рулетки; закрытие до/после фиксации снимка; смена ориентации; прерывание сети при подготовке офлайна; повреждённый/неизвестный снимок; ошибка записи; несовместимый выпуск; устаревшая вкладка. Поведение FR-05/09/11/13/15/16 и DATA_MODEL.md.

| NFR-05 Скорость | На телефоне пилота принятие действия до видимого ответа ≤300 мс вне намеренной анимации; 20 последовательных действий измерить, отчёт с максимумом. Рулетка 1,2 с. Автономный холодный запуск ≤3 с в 5 замерах; указать устройство/версии |
| NFR-06 Надёжность | Ни повторов ID, ни потери подтверждённого состояния в тестах. Не более одного перехода на одно принятое действие. Сбой хранения/обновления видим и не сбрасывает игру |
| NFR-07 Сеть и размер | Цель первого выпуска: все обязательные кешируемые ресурсы вместе ≤2 МиБ без учёта сжатия; отдельный отчёт по фактическому размеру. Ни один необходимый текст/шрифт не зависит от внешнего домена |
| NFR-08 Язык и сопровождение | Интерфейс, колода и документация на русском. Тексты колоды неизменны. Логика игры тестируется без DOM, сети и хранилища. Версии зависимостей фиксируются lockfile |

## 19. Тестирование

TEST_PLAN.md содержит T-01…T-21: контент, случайность, инварианты, восстановление, офлайн, ошибки, обновление, реальный телефон, публикация Pages, изоляция подпапки и совместимость Node/Vite. Нестабильный статистический тест не заменяет проверку алгоритма. Сборка не является доказательством автономного запуска.

## 20. Критерии приёмки

1. Все FR-01…FR-22 и NFR-01…NFR-08 проверены; результаты измерений технических параметров зафиксированы.
2. T-01…T-21 имеют результат и свидетельства; нет провалов критических сценариев. Недоступная проверка отмечена «не проверено», а не «пройдено».
3. Все 60 карточек точно совпадают с действующим Excel, распределение 21/25/14.
4. Полная игра возможна без регистрации и без сети после статуса готовности; восстановление не перевыбирает карточку.
5. Не добавлены функции за границами MVP. Проверена мобильная читаемость, добровольность и отсутствие оценки ответов.
6. Публикация main на GitHub Pages разрешена; она принята только при успешном Actions run и наблюдаемой рабочей HTTPS-ссылке. До реального Android-теста результат называется «сборка для проверки», не «пилот принят».

## 21. Ограничения

История только на одном origin в одном профиле браузера. Без экспорта и переноса между телефонами. Очистка данных/удаление кеша отменяет сохранение/автономность. Первый визит без интернета невозможен. Будущий Android — отдельный этап, не обещание готового APK.

## 22. Риски

| Риск | Мера |
|---|---|
| Рулетки отвлекают от разговора | Короткая анимация, ручной выбор всегда доступен |
| Глубокий вопрос вызывает дискомфорт | Подтверждение глубины, свободная смена и пропуск |
| Исчерпанные сочетания часто выпадают | Ясное сообщение; не менять равные шансы без согласования |
| Chrome очищает локальные данные | Объяснить ограничение в правилах, не хранить ценные ответы в MVP |
| Новый выпуск ломает снимок | Версии, отложенное обновление, отсутствие автоматического сброса |
| Эмуляция скрывает проблемы телефона | Обязательный реальный тест |
| Ссылка доступна посторонним | Обычная ссылка согласована; в игру не включать личные записи. Видимость исходного репозитория решается отдельно |
