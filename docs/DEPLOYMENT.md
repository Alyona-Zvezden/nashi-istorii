## T00: создать и подключить репозиторий

1. Создать отдельный репозиторий, предлагаемое имя nashi-istorii. Не использовать существующие проекты пользователя как замену. Главная ветка main.
2. Видимость исходников выбрать отдельно. На GitHub Free Pages поддерживает публичные репозитории; приватный репозиторий требует подходящего плана. Пользователь не разрешал покупку тарифа или автоматическую публикацию личных исходных заметок. [GitHub Pages: доступность по планам](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
3. Дать существующему подключению Codex доступ именно к новому репозиторию. Не создавать и не пересылать токены в чат. Если это требует изменения разрешений подключения, пользователь выполняет его средствами GitHub/Codex.
4. Проверить репозиторий через GitHub-коннектор, основную ветку и разрешённый рабочий checkout. Клонирование и последующая разработка относятся к этому отдельному репозиторию.
5. Перенести документы и действующую колоду. Личные TXT с контекстом и MANIFEST с абсолютными пользовательскими путями не публиковать в публичном репозитории. Перед переносом подготовить отдельный README источников с относительными путями и SHA-256; архив документации не заливать целиком без проверки состава.

## Node.js и Vite

В этой сессии найдены Node.js 24.22.1 в среде Codex и 26.13.1 в системной установке. Существующий npm — 11.20.0. Это инвентаризация, а не доказательство успешной сборки приложения. Ветки 24 и 26 указаны как LTS в [Node.js Releases](https://nodejs.org/en/about/previous-releases).

Для начала рекомендована имеющаяся ветка 24 LTS; не устанавливать новый Node.js, если текущий совместим. При T01:

- проверить node/npm, engines выбранной точной версии Vite и тестовых пакетов;
- записать выбранную LTS-ветку в .nvmrc, например 24, а фактические patch-версии в протокол;
- указать engines Node, отражающие реально проверенную совместимость, и engine-strict=true;
- зафиксировать Vite, TypeScript и тестовые зависимости с lockfile; запускать npm ci в CI;
- использовать одну ветку Node локально и в Actions, проверить typecheck, unit, build и браузерный smoke.

Документация Vite на дату проверки указывает поддержку Node.js 20.19+ или 22.12+, однако проект дополнительно требует LTS >=22. Поэтому Node 22.0 не считать автоматически подходящим. Перед установкой повторно проверить выбранную версию: [Vite Getting Started](https://vite.dev/guide/).

## GitHub Actions

Файл в рабочем репозитории: .github/workflows/deploy-pages.yml. Сначала подготовить реальные scripts в T01, затем перенести шаблон и проверить его. PR выполняет проверки без публикации. Push main и ручной запуск для main:

1. Checkout, Node из .nvmrc, npm ci.
2. Проверка Node LTS >=22 и совместимости установленных пакетов.
3. Typecheck, unit, build.
4. Playwright Chromium и E2E на production build в реальной подпапке.
5. При полном успехе загрузить только dist в Pages artifact.
6. Зависимая deploy-job с pages:write/id-token:write, environment github-pages и результатом page_url публикует выпуск.

Actions фиксируются на проверенные SHA из официальных источников; не использовать сторонние actions без необходимости. Не требуются PAT, ключи БД или отдельные серверные секреты. В настройках Pages выбрать Source=GitHub Actions. Ошибка проверок блокирует новую публикацию; предыдущая рабочая версия не удаляется.

Источник требований workflow: [GitHub custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages). Пример base и размещения: [Vite GitHub Pages](https://vite.dev/guide/static-deploy.html#github-pages). Проверено 21.11.2026; перед фактическим первым запуском проверить доступность закреплённых actions.

## Одна подпапка для всех ресурсов

Для project site формат base: /<repository>/. В примере nashi-istorii — /nashi-istorii/. Один BASE_PATH передаётся в сборку и браузерные тесты; Vite config читает его и проверяет начальный/конечный слеш. Изменение имени репозитория требует пересборки и переноса ссылки, не выполняется незаметно.

| Элемент | Правило |
|---|---|
| URL игры | https://<owner>.github.io/<repository>/ — пока формат, не работающий адрес |
| Vite base | /<repository>/, никогда / для project site |
| HTML/JS/CSS/контент | URL построены от base; отсутствуют корневые /assets/... |
| Service worker | /<repository>/sw.js, scope /<repository>/; вне scope запросы не перехватывать |
| Manifest | В подпапке; name/short_name на русском, lang=ru, display=standalone, start_url/scope/id внутри приложения |
| Иконки | Локальные PNG 192×192 и 512×512; URL от base, включены в кеш |
| Хранилище и кеш | Префикс содержит app/repository slug, чтобы не затронуть другой project site того же origin |
| Навигация | Одна страница, без серверных глубоких маршрутов и без зависимости от корневого 404-fallback |

Manifest scope и service worker scope — разные настройки, обе проверить: [MDN Manifest scope](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/scope). Установка через стандартное меню Chrome необязательна; основной сценарий — открыть ссылку.

Только production dist: HTML, JS/CSS, колода, PWA-ресурсы. Без docs, TXT/XLSX, исходного контекста, абсолютных локальных путей, тестовых отчётов, node_modules и ключей.
